# RepoMind RAG audit — 2026-10-07

RepoMind has a useful foundation: deterministic analysis, code-aware BM25, symbol-aware chunks, weighted RRF, optional neural retrieval/reranking, persisted graphs, and citation metadata. The highest-value work is to correct evidence handling and remove repeated query work before adding infrastructure or larger models.

This review covers first-party application modules, tests, evaluation fixtures, migrations, scripts, configuration, CI, deployment files, and project documentation in the current working tree, including uncommitted changes. Installed dependencies, Git internals, cloned repositories, runtime indexes/databases, and private `.env` values are outside the source review. Application code was not changed. Temporary fixture experiments used local providers and no external LLM calls.

## Verification and measurements

- Test suite: **154 passed in 7.48 seconds** (`PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m pytest -q -p no:cacheprovider`).
- Lint: **all checks passed** (`.venv/bin/ruff check . --no-cache`).
- Re-ran the 20-question fixture benchmark: hashing dense MRR 0.892, BM25 MRR 0.892, hybrid MRR 1.000, hybrid symbol recall@5 0.941. These measure the existing synthetic development fixture, not held-out answer quality.
- A repeated cached fixture answer still called the retriever once and parsed the complete chunk sidecar **five times** to get its manifest.
- Synthetic 5,000-chunk / 2.68 MB sidecar experiment: median warm retrieval over 10 runs was **26.68 ms**. Monkeypatching only `manifest()` to return the already-read manifest reduced the same retrieval to **4.87 ms**. This isolates overhead; it is not a production benchmark or an implemented optimization.
- Prompt experiment: an 80-line source was truncated before line 80, yet `long.py:80` passed citation verification. `long.py:1-9999` also passed against the declared 1–80 source because the checker accepts overlapping ranges.
- Duplicate experiment: identical `a.py` and `b.py` were indexed only as `a.py`; exact lookup of `b.py` returned no chunks despite the recorded `duplicate_paths` metadata.
- Graph experiment: `alpha` in `a.py` calls `beta` in `b.py`; `call_path()` found the edge, but `expand_files({'a.py'}, hops=1)` returned no files when there was no direct file dependency edge.
- Evidence experiment: asking “Why does a.py implement OAuth refresh token rotation?” against a file containing only `def auth(): return True` produced **strong evidence**, zero term coverage, and all four feature terms listed as absent. The named-file shortcut overrode the missing evidence.

## Fix first: correctness and consistency

### 1. Make evidence strength measure answer support, not source existence

**Priority: P0.** `app/rag/evidence.py:144–206` promotes any matching identifier or mentioned file to strong evidence before considering missing query content. The reproduction above demonstrates the false-positive file case. An identifier match establishes where code is located; it does not establish that the code implements the requested property.

Keep separate fields for source relevance, answerability, and coverage completeness. For specific questions, require support for the requested operation/property even when the source name matches. For multi-part questions, assess each requested part. A calibrated reranker can improve relevance, but its score is not proof of a claim. Remove the default “strong” status for unassessed evidence in `app/core/chat.py:23`.

Add negative fixtures that name real files/symbols while asking about nonexistent features, negated behavior, and partial multi-hop flows. Evaluate false confident answers as well as correct abstentions. For weak/absent evidence, make skipping generation configurable: today the LLM is still called and merely instructed to abstain.

### 2. Verify only the exact evidence exposed to the generator

**Priority: P0.** `app/rag/grounding.py:68–103` trims each source to 2,200 characters but retains its complete line range. `verify_citations()` at line 162 accepts any overlap, so a range can extend thousands of lines beyond the evidence and still be marked verified.

Trim at complete line boundaries, emit line numbers, and record the actual visible range. Require ordered, fully contained ranges against the exact path or an explicitly resolved unambiguous alias. Keep retrieved sources, prompt-visible sources, and cited sources distinct. Return prompt-visible citations from chat; currently the response may include sources omitted by the prompt budget, and run-question filtering can hide sources the model could cite.

The Detective has the same problem: search previews expose 400 characters but register full chunk ranges (`app/agent/tools.py:99`), symbol lookup registers full definition ranges without reading the bodies, and observations are truncated after evidence registration (`app/agent/detective.py:97–101`). `file_neighbors` even registers an unrestricted path range. Distinguish structural metadata evidence from inspected source text and build citation permissions after observation packing.

After fixing structural checks, add claim-to-source validation as an optional stage for high-assurance answers. Report structural citation validity separately from semantic support; the present `grounding_score` is based on regexes and cited lines, not verified factual entailment.

### 3. Publish immutable analysis generations

**Priority: P0.** `app/core/repo_analyzer.py:140–193` replaces the dense index first, then graph, then metadata. Each file replacement is atomic, but the analysis as a whole is not. Chat queries do not acquire the analysis lock. A query during refresh or a failure after indexing can therefore mix old metadata with new vectors/graph/source files.

Write a complete generation under `data/.../<repo>/<generation>/`, validate it, then atomically publish an active-generation pointer. Pin each request and agent investigation to one generation. Include commit SHA, file hashes, parser/chunker/tokenizer versions, model revision, embedding settings, and index integrity checks in its manifest. Check that dense artifacts actually exist and match chunk counts; `VectorStore.exists()` currently checks only sidecar compatibility.

`cache_ready()` also does not invalidate analysis after ingestion/chunking/parser policy changes. Version those policies so changed limits or duplicate policy do not keep returning old coverage. Retain the previous complete generation if refresh fails.

### 4. Remove shared mutable state from concurrent analysis stages

**Priority: P0/P1; concurrency risk identified by code review, not reproduced under load.** Two different repositories can be analyzed simultaneously by the default two-worker executor, but both use the same scanner, parser cache, chunker, graph builder, and weakness detector.

`last_scan_stats`, `Chunker.last_stats`, `CodeGraphBuilder.last_graph`, and `WeaknessDetector._repo_id` are mutable instance fields. Per-repo locks do not isolate those fields across different repos. Another build can replace `last_graph` between `build()` and the analyzer reading it, or change the repo id used to generate weakness ids.

Return typed stage results containing the graph/stats rather than reading shared “last” fields. Pass repo ids explicitly to finding factories. Create parser instances per worker/task where required by the parser backend. Add barrier-controlled concurrent tests for two repos and concurrent refresh/search. This is necessary before relying on background parallelism for throughput.

### 5. Preserve duplicate-file identity while sharing embeddings

**Priority: P1.** `app/parsing/chunker.py:70–139` deduplicates solely by content hash. Retrieval helpers at `app/rag/vector_store.py:279–312` never resolve `duplicate_paths`; graph range lookup on the duplicate path also fails. Identical files in different packages can have different roles and import environments, so collapsing identity loses meaning.

Store one vector per compatible content representation but retain all file/symbol identities and an alias-to-canonical range index. Generate citations for the path actually requested. Do not discard alias paths after the 20-path metadata sample; keep the full mapping outside display samples. Include role/language/context in dedup compatibility, or deduplicate embeddings without deduplicating chunks.

## Remove avoidable latency and indexing cost

### 6. Load the index once per request and make warm loads cheap

**Priority: P1; measured bottleneck.** `VectorStore.load()` at line 213 calls `compatibility_problem()` before the memory-cache check. That calls `manifest()`, which JSON-parses the entire sidecar—including every chunk. Dense, lexical, file/range, and evidence channels repeat this work.

Put the manifest in a small separate file or validate the cached manifest against an atomic generation id/stat signature. Obtain one immutable `LoadedIndex` per request and pass it to channels. Add `positions_by_file`, symbol-to-chunk, and interval indexes so file/range retrieval avoids repeated full scans. Reuse BM25 query scores between file channels. Precompute token sets used by local reranking and evidence assessment.

Acceptance criterion: a warm retrieval performs no full chunk-sidecar deserialization. Benchmark p50/p95 with 500, 5,000, and larger chunk sets under concurrent readers.

### 7. Check answer caches before retrieval and strengthen cache identity

**Priority: P1.** `ChatService.answer()` at line 58 retrieves before checking the cache. This saves LLM tokens but still pays all retrieval/reranking costs. `_cache_key()` at line 127 includes provider name, not model, prompt version, index generation, or retrieval settings; it lowercases queries even though literal code identifiers can be case-sensitive. It hashes two history turns while generation sees four.

Resolve the lightweight generation/provider identity, then check the cache. Key by exact or identifier-preserving normalized query, effective conversation context, generation, model configuration, prompt version, and retrieval settings. Use separate bounded retrieval and answer caches. Avoid indefinitely caching transient provider failures; expire fallback answers or distinguish them from successful provider results. Coalesce concurrent identical requests. Preserve debug output when a cached answer is requested with `debug=true`.

### 8. Reuse unchanged parsing and embeddings on refresh

**Priority: P1.** Force refresh currently rebuilds everything. Chunk ids at `app/parsing/chunker.py:19` hash location and symbol but not content, so they cannot serve as content-change keys. The scanner already calculates hashes, but those are not persisted as a reusable indexing manifest.

Store file hash, parser version, chunk hash, embedding-input hash, model revision, and context version. Diff commits, update changed/deleted files, reuse unchanged vectors and parse results, then repair affected graph edges. Keep location identity separate from content/cache identity. Account for changed imports or headers that affect otherwise unchanged chunk representations. Batch missing embeddings and persist their cache on disk.

### 9. Tune resource use before replacing storage

**Priority: P2.** At the current 5,000-chunk cap, a 512-dimensional float32 matrix is about 10.24 MB. Exact NumPy search can be appropriate; JSON objects, repeated parsing, and tokenization may dominate instead. The measured experiment supports optimizing that path first.

Use byte-budgeted caches rather than “six repos” / “eight graphs” limits, consider memory-mapped immutable NumPy matrices, and profile cold BM25 construction and duplicate chunk storage in DB/JSON. Persist lexical indexes if cold loads become material. Move to ANN when measured corpus size, concurrent traffic, or p95 latency justifies it; quantify recall loss.

Postgres/pgvector can simplify server operations, but it will not fix chunking, faithfulness, or cache bugs. Preserve a dedicated lexical index; PostgreSQL built-in full-text ranking should not be relabeled BM25 without implementing that ranking. Redis/distributed workers belong after generation consistency and concurrency isolation are correct.

## Improve retrieval quality per token

### 10. Use token-aware retrieval units and parent context

**Priority: P1.** `Chunker` uses 80-line windows and permits a symbol up to 120 lines as one chunk. Small classes swallow methods into a class chunk. This loses independent method ranking; a long method may exceed an embedder's usable input and then be truncated differently by the reranker and generator.

Retrieve method/function or statement-level children, retain parent ids, and expand only the required class signature, imports, constants, and adjacent code after ranking. Budget chunks with the active model tokenizer and reserve space for contextual headers. Keep source spans precise; context additions need their own provenance. Parse Markdown fences/tables and JSON/YAML/TOML sections structurally where line windows split useful units. Distinguish real one-line AST definitions from regex spans rather than extending every `end == start` symbol to the next definition.

The configured semantic default truncates inputs longer than 256 word pieces, according to its [model card](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2). An 80-line chunk can easily exceed that limit; simply enabling semantic embeddings can make its tail invisible to dense retrieval.

### 11. Add semantic capability with model-specific encoding and evaluation

**Priority: P1/P2.** The default hashing dense channel is lexical and correlated with BM25. Optional MiniLM and MS MARCO models are general-purpose choices. `SentenceTransformerEmbedder` sends documents and queries through the same `encode()` path (`app/rag/embeddings.py:70–88`).

Evaluate code-relevant and mixed prose/code encoders on held-out repos, including CPU latency, memory, input limits, and language coverage. Support each model's required query/document prompts and normalization; current [Sentence Transformers guidance](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html) recommends `encode_query()` / `encode_document()` for retrieval. For models without task-specific settings, those methods can produce the same encoding, so this API change alone is not a quality gain.

Version model revision, prompt, pooling, normalization, and max sequence length in the index fingerprint. Expose fallback/degraded status for both embeddings and reranking; explicit requested semantic providers currently fall back to hashing if unavailable. Do not select a larger model based only on benchmark reputation or assume it beats the tuned lexical baseline.

### 12. Make graph expansion follow the relationships relevant to the question

**Priority: P1.** `GraphIndex.expand_files()` starts from file nodes and inspects one adjacent edge. Calls between functions are two structural steps away, so they are missed without a direct file-import edge. Folder nodes can also enter the expansion result, wasting its bounded budget.

Build a cached file adjacency graph from symbol-level calls/imports/inheritance, or traverse from matched symbols explicitly. Expand callers for “who calls” and callees for “how it works.” Retrieve the actual callsite and the target definition. For multi-hop questions, expand one bounded frontier at a time, stopping when required subquestions are covered. Carry edge confidence and resolution provenance; `callers()` / `callees()` currently discard confidence, and low-confidence name matches can be described like confirmed calls.

`call_path()` rebuilds an edge-filtered graph each time: cache that view per generation. Preserve multiple relation types/callsites rather than losing them through a single `DiGraph` edge. In tool relation evidence, distinguish a callsite line in the caller file from a callee definition line; the same `line` attribute is currently interpreted against whichever row file is returned.

### 13. Make query planning consistent and bounded

**Priority: P2.** `HybridRetriever.retrieve()` classifies the original question, rewrites afterward, and resolves mentioned files from the original query. The rewritten symbols can therefore be searched with an inappropriate intent/priority plan. Follow-ups only carry tokenized words from one user turn.

Resolve referents into a structured standalone query, then classify and resolve file/symbol constraints. Retain case-sensitive paths/symbols. Handle distinct identifiers and intent words separately so filenames do not automatically become function questions. Decompose multi-part/multi-hop questions into at most a few subqueries; do not add indiscriminate LLM expansion to every request. Use stable ordering before limits: set iteration in symbol/file/graph selection currently creates avoidable tie variability.

### 14. Tune fusion and reranking with ablations, not more fixed weights

**Priority: P2.** Retrieval always uses dense@30, lexical@30, fused@40, and a fixed per-file cap of three. Related channels (hashing/BM25; facts/priority) can count correlated evidence multiple times. Some intent overrides use `max()` so a requested lower weight does not actually lower a default weight.

Make candidate counts/weights configurable and log channel contributions. Protect exact symbol matches, test query-dependent candidate budgets, and diversify by requested evidence roles/novelty rather than a fixed per-file count. Questions about a large single file can need more than three chunks. Rerank complete token-budgeted passages instead of the first 2,000 characters (`app/rag/rerank.py:73`).

The cross-encoder converts its output through a sigmoid and labels it calibrated, but no held-out calibration is performed; some model configurations may already output transformed scores. Inspect the actual activation, preserve raw scores, calibrate answerability separately, and handle inference errors with a logged local fallback. Benchmark each channel's marginal quality and latency contribution.

### 15. Pack context around the question and measure token use

**Priority: P1/P2.** `GroundedPromptBuilder` budgets only source blocks, not facts, graph, history, question, system rules, or output reserve. It truncates chunk heads rather than selecting relevant spans. The facts block always spends space on run instructions, even for unrelated code questions.

Use the generator tokenizer when available and a conservative documented fallback otherwise. Budget the entire request. Select relevant spans, merge redundant overlapping context, include needed parent/import context, and retain complete visible line ranges. Attach source ids to derived facts, graph claims, and static findings so those are auditable too. Measure useful evidence per input token, actual input/output tokens, and generation latency. Streaming improves perceived latency; track time to first token separately from total response time.

## Preserve repository coverage and parser fidelity

### 16. Allocate indexing budgets across modules and roles

**Priority: P1/P2.** Whole-file chunk admission is ordered docs → code → config → tests, then shallow paths. A long important file can be rejected entirely; large docs can crowd out implementation and tests. The scanner itself is lexicographic and stops at caps before relevance can be considered.

Use a cheap metadata pass, sample representatives across packages/roles, reserve test/config budget, prioritize entrypoints and graph-central files, and admit important symbols from oversized files. Record complete omitted-file inventories in a compact catalog. Allow bounded on-demand retrieval/indexing for a requested omitted file. `RepoFacts.file_tree` is only 80 paths, so it is not a complete retrieval catalog.

Coverage currently reports partial only for repository/file-count and chunk caps. Per-file truncation, unsupported encodings, binary docs, and parser failure can still coexist with an apparent 100% analyzed fraction. Report scan coverage, text coverage, parse coverage, and searchable coverage separately. Pass those limitations into answerability and the prompt; “not found in indexed text” must not become “absent from the repository.”

### 17. Strengthen language-aware symbol and import extraction

**Priority: P2.** Python parse failures return empty results but are still labeled `python-ast`. Tree-sitter error nodes are not assessed. JavaScript `.jsx` files use the JavaScript grammar rather than a JSX-specific selection, while `.tsx` is handled specially. Regex scope never reliably resets, making call ownership approximate.

Report backend, parse success, error spans, and confidence per file. Fall back to tolerant extraction for truncated/invalid Python and failed grammars. Preserve `from x import y as z` bindings and original/imported names for JS aliases/default imports; current extraction drops information needed for reliable call resolution. Read actual `tsconfig`/workspace aliases instead of assuming `@/` means `src/`. Add language-specific fixtures for methods, exports/reexports, arrow functions, Go receivers, JSX/TSX, and package layouts.

Keep machine-generated lockfiles out of raw semantic retrieval, but index derived dependency/version facts with exact provenance. Non-UTF8 text and notebooks should have explicit policies: notebook cell extraction is more useful than embedding raw JSON, and a lockfile truncated into invalid JSON should report incomplete dependency inventory.

## Evaluation, observability, and product work

### 18. Replace the development fixture as the main quality signal

**Priority: P1.** The existing 20 questions are useful regression checks but were written/tuned on one fixture. `_metrics()` (`evals/run_eval.py:59`) calls any expected-file hit “recall”; with multiple gold files, that is success/hit rate, not fraction-of-gold recall. Symbol scoring counts an entire class chunk as finding any method within it. `build_environment()` forcibly selects local providers, so passed model settings do not create a controlled semantic experiment.

Add a local snapshot dataset of multiple real repos pinned to SHAs, split tuning and held-out repos, and keep routine tests offline. Define gold evidence spans, alternative sufficient evidence, and jointly required evidence separately. Include unanswerable, misleading-name, long-file, duplicate-path, language, and conversational cases.

Report hit@k, true evidence recall@k, MRR/nDCG, citation precision/coverage, supported-claim rate, multi-hop completion, answer correctness, and abstention precision/recall. Use bootstrap intervals and per-intent/language/size slices. Ablate BM25, dense, symbols, graph, reranker, chunking, and context packing. Compare semantic models through an explicit reproducible CLI/config matrix, with failures/fallbacks visible. Add latency/memory/token budgets to CI using controlled broad tolerances rather than fragile millisecond assertions.

### 19. Trace costs and expose evidence status consistently

**Priority: P2.** Retrieval traces currently contain selected scores/channel ranks but no stage timings. Add scan/parse/embed/index/load/dense/BM25/graph/rerank/pack/generate/verify timings, candidate counts, cache hits, visible/dropped evidence, tokens, model identities, and generation id.

Expose evidence/coverage/generation on search and MCP answers; search omits answerability, and MCP `ask_repository` drops `evidence_strength`/`evidence`. Show “retrieved,” “shown to model,” “cited,” and “claim supported” as separate states in Streamlit. Label the current score as citation validity rather than factual grounding. Add streaming answers after correctness is established. Use connection pooling for LLM HTTP calls and request deadlines that include retries, plus bounded model inference concurrency.

### 20. Make derived analysis queryable without relying on presentation summaries

**Priority: P2.** Facts and drift collectors consume the bounded API graph rather than the complete graph. Relational symbol/edge tables are also populated from that truncated serialization. Larger repos can lose routes, symbols, and facts even while the full graph exists on disk. Summary output truncates dependency vulnerabilities/drift findings; chat's deterministic weakness path answers from a general list rather than selecting question-relevant findings.

Use full graph indexes and typed analysis results as internal inputs; truncate only at API/UI display boundaries. Persist full structured findings with source spans and provide dedicated retrieval channels for dependency, weakness, drift, and history questions. Keep deterministic extraction separate from inference. Parse manifests structurally (for example with TOML parsers), validate inferred run commands against actual package metadata, and prefer verified code/config over drifted docs while clearly explaining conflicts.

### 21. Keep deployment and repository hygiene reproducible

**Priority: P3.** Lock tested dependency/model revisions for reproducible optional backends, while allowing deliberate updates. The source has an unrelated Codex-only `package.json`, untracked `node_modules`, and no `node_modules/` exclusion in `.gitignore`/`.dockerignore`; this inflates build context and misleads the project's own dependency scanner. Keep local development tooling outside runtime manifests or explicitly label it, and exclude installed/generated directories. The app need not add a new orchestration framework to implement these improvements.

## Suggested implementation sequence

1. **Evidence correctness:** named-source false confidence, visible-span citations, strict range checks, agent evidence provenance. Add regression tests for the reproduced cases.
2. **Snapshot correctness:** immutable generations, explicit stage outputs, cross-repo concurrency isolation, artifact integrity/version checks.
3. **Fast query path:** cached manifest/index handle, file/range indexes, early answer-cache check and correct cache keys. Re-run the 5,000-chunk profile.
4. **Quality baseline:** held-out local repo snapshots, true evidence metrics, negative/conversational cases, channel ablations.
5. **Higher-quality retrieval:** tokenizer-aware child/parent chunks, corrected graph expansion, parser/import fixes, model-specific embeddings and measured reranking.
6. **Lower refresh cost:** content-addressed parse/embedding cache and incremental index/graph updates.
7. **Scale only when measured:** memory budgets, ANN/storage consolidation, distributed jobs/cache, pooled clients and streaming.

Acceptance should require improvements to held-out evidence recall/faithfulness without unacceptable p95 latency, memory, or token growth. Model/backend changes must retain the tested deterministic local fallback.
